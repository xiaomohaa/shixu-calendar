# 项目：开发一款 macOS 风格的个人 CalDAV 日历客户端

你是一名资深桌面应用开发工程师、前端 UI/UX 设计师和 CalDAV 协议工程师。请直接在当前项目中开发一款真正可用的个人日历客户端，而不是仅生成设计稿、原型或演示页面。

## 一、项目目标

开发一款运行在 **Windows 10/11 x86-64（x64）** 上的独立桌面日历应用。

产品定位：一款简洁、美观、流畅、注重隐私的个人 CalDAV 客户端，界面风格参考 macOS 原生日历应用。

核心要求：

1. 用户可以在设置中自行配置 CalDAV 服务器地址、用户名和密码。
2. 支持自动发现 CalDAV 服务，也允许用户手动填写服务器地址。
3. 支持连接测试、日历列表获取和双向同步。
4. 支持创建、编辑、删除、查询日程。
5. 支持月视图、周视图、日视图和日程列表视图。
6. 支持多个日历、离线查看、同步状态显示和异常处理。
7. 所有主要界面使用简体中文，界面布局精致，操作符合现代桌面应用的使用习惯。
8. 最终生成可在 Windows x64 上安装和运行的应用程序。

不要将 CalDAV 地址写死在代码中，不要绑定任何特定服务商。应尽量兼容 Nextcloud、iCloud、Radicale、Baïkal 及其他符合标准的 CalDAV 服务，具体兼容性以实际协议支持为准。

## 二、技术栈

请采用以下技术栈，除非发现明确的兼容性问题，否则不要随意更换：

- 桌面框架：Electron
- 前端：React + TypeScript
- 构建工具：Vite
- UI：自定义组件，优先使用轻量、统一的组件方案
- 图标：Lucide
- 日历布局：使用成熟的日历组件或自行构建可靠的日历视图
- CalDAV 客户端：优先评估并使用 `tsdav`
- iCalendar 解析和生成：使用 `ical.js`
- 本地数据库：SQLite
- 数据校验：TypeScript 类型约束及必要的运行时校验
- 自动化测试：Vitest，协议和核心逻辑测试优先

请在实现前确认依赖包的当前 API、兼容性和许可信息，不要臆造库函数。

Electron 主进程负责网络访问、CalDAV 协议、数据库和敏感信息处理。Renderer 渲染进程只负责界面和用户交互。

安全要求：
- 开启 `contextIsolation`。
- 禁用 Renderer 的 Node.js 集成。
- 通过受限、经过类型约束的 IPC 暴露必要能力。
- 不允许 Renderer 直接访问任意文件、执行系统命令或读取敏感凭据。
- 合理配置 Content Security Policy。

整体视觉关键词：

- 简约、精致、现代。
- 适当使用圆角、细边框、柔和阴影和充足留白。
- 采用清晰的字体层级、统一的间距和对齐规则。
- 浅色模式与深色模式均需完整设计。
- 动画克制、自然，不影响操作效率。
- 窗口缩放时布局自适应，不出现组件重叠或内容溢出。
- 使用高质量的 Lucide 图标，避免 Emoji 充当正式功能图标。
- 不使用廉价的渐变背景、过度玻璃拟态或大量装饰性卡片。
- 默认简体中文，确保中文标题、日期和长文本排版正常。

## 五、CalDAV 连接和账户设置

这是整个项目最重要的功能之一，必须真正实现，不能使用假数据模拟连接成功。

### 1. 添加 CalDAV 账户

提供清晰的账户配置界面，字段包括：

- 账户名称。
- CalDAV 服务器地址。
- 用户名。
- 密码或应用专用密码。
- 可选的高级连接参数。

服务器地址示例可以放在占位符中，但不能将示例地址当成默认有效账户。

界面提供：

- 测试连接。
- 自动发现服务。
- 保存账户。
- 取消。
- 清晰的连接错误提示。

### 2. CalDAV 服务发现

尽可能按照标准流程实现：

1. 规范化并验证用户输入的 URL。
2. 在支持的情况下尝试 `/.well-known/caldav`。
3. 通过适当的 WebDAV `PROPFIND` 请求发现当前用户主体。
4. 获取 `calendar-home-set`。
5. 获取账户下的日历列表。
6. 读取日历名称、颜色、支持的组件类型和其他可用属性。
7. 如果自动发现失败，允许用户填写更具体的服务地址或日历地址。
8. 将 401、403、404、405、409、429 和 5xx 等错误转化为用户可理解的提示，并保留必要的诊断信息。

不能假设所有服务商都使用相同的 URL 路径，也不能假设所有服务器都支持同一种发现方式。

### 3. 认证和安全

- 优先支持通过 HTTPS 使用 HTTP Basic 认证，以及服务器实际支持的其他认证机制。
- 不得将用户名和密码硬编码在源码中。
- 使用 Electron `safeStorage` 或经过验证的操作系统安全凭据存储方案保护凭据。
- 不得将明文密码写入普通配置文件、日志或数据库。
- 默认验证 TLS 证书。
- 不允许为了绕过证书错误而全局关闭 TLS 验证。
- 对 HTTP 明文连接或自签名证书的特殊处理必须由用户明确选择，并显示安全提示。
- 不在错误日志中输出 Authorization 请求头、密码、访问令牌或其他敏感信息。

### 4. 账户管理

设置页面支持：

- 添加多个 CalDAV 账户。
- 修改账户信息。
- 测试连接。
- 手动同步。
- 查看最近同步时间。
- 查看最近错误。
- 暂停或恢复账户同步。
- 删除账户。
- 管理每个账户下的日历。
- 为不同账户选择显示的日历。

删除账户前明确提示用户，并说明本地缓存的处理方式。不得在未确认的情况下删除远程服务器上的日历或事件。

## 六、CalDAV 同步引擎

必须将同步引擎与 UI 分离，设计成独立、可测试的模块。

实现时优先复用成熟 CalDAV 库；若其功能不足，再补充必要的协议实现。

至少考虑以下协议和数据：

- `PROPFIND`
- `REPORT`
- `calendar-query`
- `calendar-multiget`
- `PUT`
- `DELETE`
- `ETag`
- `sync-token`（服务器支持时）
- `UID`
- iCalendar / RFC 5545 数据格式

具体实现应以所使用库的实际能力和服务器支持为准。

### 同步要求

1. 首次连接时获取可用日历并进行初始同步。
2. 服务器支持增量同步时优先使用增量同步机制。
3. 不支持增量同步时采用适当的查询和回退机制。
4. 通过稳定的事件 UID 和服务器资源标识避免重复创建。
5. 正确处理 ETag 和条件更新，尽可能避免覆盖他人修改的数据。
6. 支持本地创建、修改和删除操作向远程同步。
7. 支持远程新增、修改和删除事件反映到本地。
8. 同步过程应具备超时、重试、取消和错误恢复能力。
9. 避免重复同步、重复创建事件以及多个并发同步任务互相覆盖。
10. 同步期间向用户显示真实的同步状态，而不是简单切换为成功。

### 冲突处理

当本地与服务器同时修改同一个事件时：

- 检测版本冲突。
- 不应盲目覆盖远程版本。
- 尽可能保留本地修改和远程版本。
- 向用户显示冲突提示，并提供查看和选择处理方式的入口。
- 对暂时无法解决的冲突，保留待处理状态，不得静默丢弃用户修改。

### iCalendar 数据兼容性

- 正确处理 `VEVENT`。
- 尽可能支持 `RRULE`、`RDATE`、`EXDATE` 和 `RECURRENCE-ID`。
- 正确处理 `DTSTART`、`DTEND`、`DURATION`、`TZID` 和全天事件。
- 尽可能保留 `VALARM` 提醒。
- 处理转义字符、换行折叠、UTC 时间和浮动时间。
- 修改事件时尽量保留未知属性及不由本应用管理的字段。
- 不要把服务器返回的 ICS 数据简单解析成几个字段后重新生成，导致其他属性丢失。

## 七、本地数据库和离线使用

使用 SQLite 保存必要的本地缓存和同步状态。

建议设计以下数据实体：

- accounts：账户基本信息。
- calendars：远程日历信息。
- events：本地事件索引及必要的展示数据。
- event_resources：远程资源标识、ETag 和原始 ICS 数据。
- sync_state：同步令牌、同步时间及状态。
- pending_operations：尚未成功提交到服务器的操作。
- conflicts：待处理的同步冲突。

可根据实际架构调整表结构，但必须明确数据之间的关联和唯一性约束。

要求：

- 应用重启后仍能读取已缓存的日程。
- 网络暂时不可用时，仍可浏览本地日历。
- 支持必要的离线修改，并在重新连接后尝试同步。
- 对未成功同步的修改进行持久化，避免应用退出后丢失。
- 正确区分待同步、同步成功和同步失败状态。
- 避免将同一个远程事件重复写入数据库。
- 数据库结构变更必须有迁移方案。

## 八、提醒和日期时间处理

- 正确处理全天事件和跨天事件。
- 正确处理用户配置的时区。
- 默认使用系统本地时区，并允许手动设置。
- 处理夏令时切换。
- 尽可能读取和保存 iCalendar 中的时区定义。
- 对重复事件进行合理的实例展开。
- 支持读取常见的 `VALARM` 数据，并实现适当的本地提醒能力。
- 如果某种远程提醒能力依赖服务器或操作系统支持，应在界面中准确说明，不能声称已经支持但实际没有生效。
